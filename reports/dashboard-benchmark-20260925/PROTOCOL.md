# 사전 고정 비교 프로토콜 · 2026-09-25

- **과제:** 동일한 `data.json`(기존 실작업 3쌍), 동일한 프롬프트, 같은 Main `gpt-6-sol`/`high`로 실행하는 독립적인 소형 정적 대시보드 개발. native는 Jev off, active는 Jev active. 각각 native Agent의 범위 제한 조사 1회만 요구한다. 각 실행은 별도 임시 HOME·저장소 복사본·git 스냅샷, 최대 48턴, CLI 예산 상한 $3, 벽시계 720초. 이 상한은 성과 목표가 아니며 어느 조건의 모델/제공자 내부 추론 동등성도 보장하지 않는다. 양쪽에 동일한 외부 채점기를 사용한다.
- **입력 무결성:** 모델은 `dashboard/data.json`을 수정할 수 없고 `dashboard/index.html`, `dashboard/styles.css`, `dashboard/app.js`만 변경한다. 네트워크·패키지 설치·자격 증명 읽기 금지. 앱은 로컬 HTTP에서 빌드 단계 없이 실행되어야 한다.
- **제품 목표:** 3건의 작업에 대해 정확한 native/active 비교(기능 수용 2/3 대 3/3, 총 경과 시간 359.338초 대 557.244초, active 시간 +55.1%) 및 각 task의 기능/자기 테스트·CLI 표시 비용. 미확인 청구 총비용과 내부 추론량을 사실처럼 표시하지 않는다. 한국어 UI, 반응형 화면, 레이블·실제 버튼·키보드 사용 가능, 명확한 empty state.
- **고정 브라우저 수용 9사례:** (1) 초기 지표·3행·비용 경계, (2) active-only 필터 1행, (3) 작업 필터 1행, (4) 교차 필터 0행·empty state, (5) 초기화 3행, (6) 양방향 시간 정렬, (7) 마우스 상세 보기, (8) 버튼 포커스 + Enter 상세 보기, (9) 390×844 모바일의 주요 컨트롤 및 문서 너비. 매 사례 실제 loopback HTTP 서버 + Chrome CDP, 콘솔/네트워크 오류도 실패. 각 사례 1점(총 9점); 실패 원인 기록. 기능 검사 통과와 미적 품질은 구분하고 스크린샷을 직접 본 후 시각·읽기·정보 구조의 구체적 장단점을 기술한다. Lighthouse/장애인 사용자 테스트를 했다고 주장하지 않는다.
- **계측:** 시작/종료 wall clock UTC, subprocess 실제 경과 시간, CLI의 최종 `usage` 원본(입력/출력/cache creation/cache read) 및 `total_cost_usd` 표시값. 별도 child typed usage가 관측되면 식별자별로 독립 기록하고 Main 총계에 무턱대고 더하지 않는다. Jev HTTP `response.usage`를 별도 합계로 기록한다. 누락 필드는 `null`, 청구 총액은 `unknown`. 완료, 바뀐 파일, 실제 라우팅 관측, 최초 시도 완료는 각각 따로 기록한다.
- **선행 파일:** `data.json`과 `browser-grade.py`/브라우저 CLI의 SHA-256은 모델 실행 전에 기록한다. 원본 데이터에서 계산을 검산하고 고정 테스트를 소급 완화하지 않는다. 결과 후 추가 탐색 검사는 별도 분류한다.
- **해석:** 소형 웹 1쌍만으로 Jev의 일반 우월성/통계적 우위 주장 금지. 이전 코드 유지보수 과제와 새 웹 과제는 난이도와 범위가 달라 같은 품질 분모에 혼합하지 않는다.
