# Outcome collector on the real-session evidence, 2026-11-25

Output of `orchestration/scripts/collect.mjs` (the outcome collector, `docs/KERNEL.ko.md` section "결과 수집기") run
offline on the hook state and transcripts of the two paired-pilot sessions and on the hook state of the re-check
session. Produced by `qa/kernel/collector/run-pilot-evidence.sh <evidence root> <work dir> <this folder>`.

## What these files are

| File | Content |
|---|---|
| `summary-armA.json`, `summary-armB.json` | The collector's JSON summary for each pilot arm (real run on a copy of the hook state, with the verification file) |
| `summary-armB.second-run.json` | The same command again on the same state: 0 labels and 0 observations written (517 and 8 already present) |
| `summary-arm{A,B}.with-context.dry-run.json` | Dry run with `--evaluation-context pilot-20261125`: shows which withholding reasons remain once a context is named |
| `summary-recheck.state-only.json` | The re-check session (skills + supervisor active, after the re-issue fix): hook state only, because its transcripts were not kept |
| `observations-arm{A,B}.jsonl` | The observation records the collector wrote (8 per arm), as stored |
| `observations-report-arm{A,B}.json` | `collect.mjs --report` over those records |
| `calibration-armB.observed-load.json` | `decisions.mjs --action report --point delegation.skills --source observed-load` on arm B after collection |
| `calibration-armB.observed-load.by-question.json` | The same labels split into the `need` question and the per-skill questions (`qa/kernel/collector/calibration-by-question.mjs`; metrics from the product's `calibrationReport`) |
| `calibration-armB.all-sources.json` | The unfiltered report: both label sources, each marked weak, with per-source metrics |
| `verification-arm{A,B}.json` | The verification files given to the collector: one entry per pilot task (task hash, passed, conventionPassed, validator id, artifact hash) |
| `verification-arm{A,B}.summary.json` | Per pilot task id: delegated, passed, conventionPassed, as the pilot checker reported them |

Verification files were generated by `qa/kernel/collector/make-verification.mjs`, which runs the pilot's scripted
checker (`qa/kernel/pilot/checkers/check.mjs`, not modified) on each project. Validator name `pilot-checker`, version
= SHA-256 of `check.mjs`; `artifactSha256` = SHA-256 of the checker's JSON output as its CLI prints it. The checker
output itself contains project content and stays outside the repository.

## What these files are not

- Not evidence that skill injection or routing improves anything. The pilot baseline passed everything in both arms.
- Not ground truth for "which skill was needed". `observed-load` says what a subagent did. A subagent may load a
  skill it does not need and skip one it needs, and in arm B the injected block itself asks it to load. The 7 false
  negatives on `need` are judgments below 0.5 followed by a load; these labels cannot tell a judge miss from an
  unnecessary load. `external-verification-with-load` adds that the task passed its convention check; the pass is
  not attributed to the skill.
- Not a calibration of `supervisor.outcome`: the pilot sessions had the supervisor off, and the re-check session's
  three judgments have no external verification, so no supervisor label exists.
- Not an end-to-end run of the post-fix shape (`delegation_reissued`) on real transcripts: the re-check session's
  transcripts were not kept. That path is covered by tests with synthetic transcripts only.
- Not imported anywhere: the evidence store of every state copy is untouched, and no evaluation row exists.
- Not a statement about other hosts: the only transcript shapes read are Claude Code desktop 2.1.330 in permission
  mode auto (two sessions). Codex transcripts were never observed and are unsupported.
- No prompt text, report text, local path, session id, agent id or tool-use id is in these files. Ids are SHA-256
  hashes; skill names are the validated names of the pilot's synthetic catalog.
