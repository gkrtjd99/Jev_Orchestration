# Outcome collector on the real-session evidence, 2026-11-25, after review (r2)

Output of `orchestration/scripts/collect.mjs` (`outcome-collector-2`; `docs/KERNEL.ko.md` section "결과 수집기") run
offline on the hook state and transcripts of the two paired-pilot sessions and on the hook state of the re-check
session. Produced by `qa/kernel/collector/run-pilot-evidence.sh <evidence root> <work dir> <this folder>` (exit 0).

**This folder supersedes `../collector-20261125/`**, which holds the output of the collector before review
(`outcome-collector-1`) and is left as it was. What was wrong there and is corrected here:

- `need` was labelled "any project skill was loaded in the delegation" on every judge request, although each request
  asks `need` about its own skills only. 6 of the 7 "false negatives on need" reported there were produced by that
  rule, not by the judge. Here `need` of a request is true only when one of that request's skills was loaded.
- Labels from delegations whose prompt carried the skills block of the decision being labelled were mixed with the
  others under one source. They now have their own sources (`...-after-injection`).
- The calibration report said `"sufficient": true` for 496 weak question labels on 16 decisions. Sufficiency now
  counts labelled decisions and is never true for weak labels.
- A recursive search from the project root was read as "no skill access". It is now indeterminate, so 6 of the 16
  delegations (A 4, B 2) give no load label.

## What these files are

| `summary-armA.json`, `summary-armB.json` | The collector's JSON summary for each pilot arm (real run on a copy of the hook state, with the verification file) |

| `observations-arm{A,B}.jsonl` | The observation records the collector wrote (8 per arm), as stored |
| `observations-report-arm{A,B}.json` | `collect.mjs --report` over those records |
| `calibration-armB.observed-load.json` | `decisions.mjs --action report --point delegation.skills --source observed-load` on arm B: delegations WITHOUT a skills block in the prompt |
| `calibration-armB.observed-load-after-injection.json` | The same for `observed-load-after-injection`: delegations WITH the block of the labelled decision in the prompt (decision-influenced) |
| `calibration-armB.<source>.by-question.json` | Each of the two split into the `need` question and the per-skill questions (`qa/kernel/collector/calibration-by-question.mjs`; metrics from the product's `calibrationReport`), with labelled decisions against all decisions of the point |
| `calibration-armB.all-sources.json` | The unfiltered report: four label sources, each marked weak, with per-source metrics |
| `verification-arm{A,B}.json` | The verification files given to the collector: one entry per pilot task (task hash, passed, conventionPassed, validator id, artifact hash) |
| `verification-arm{A,B}.summary.json` | Per pilot task id: delegated, passed, conventionPassed, as the pilot checker reported them |

Verification files were generated by `qa/kernel/collector/make-verification.mjs`, which runs the pilot's scripted
checker (`qa/kernel/pilot/checkers/check.mjs`, not modified) on each project. Validator name `pilot-checker`, version
= SHA-256 of `check.mjs`; `artifactSha256` = SHA-256 of the checker's JSON output as its CLI prints it. The checker
output itself contains project content and stays outside the repository.

## What these files are not

- Not evidence that skill injection or routing improves anything. The pilot baseline passed everything in both arms.
- Not ground truth for "which skill was needed". `observed-load` says what a subagent did, and a subagent can produce
  a load with one call. `...-after-injection` labels were produced after the decision itself asked for the load.
  `external-verification-with-load` adds that the task passed its convention check; the pass is not attributed to the
  skill. The collector has no way to produce a verified "this skill was needed" label.
- Not a random sample of decisions. A decision is labelled only when its delegation was routed, launched, joined to
  a finished readable subagent transcript with determinate skill access and a known block state, and the decision
  was the one applied to the launched call.
- Not a calibration of `supervisor.outcome`: the pilot sessions had the supervisor off, and the re-check session's
  three judgments have no external verification, so no supervisor label exists.
- Not an end-to-end run of the post-fix shape (`delegation_reissued`) or of a shadow-mode session on real
  transcripts: the re-check session's transcripts were not kept. Those paths are covered by tests with synthetic
  transcripts only.
- Not imported anywhere: the evidence store of every state copy is untouched, and no evaluation row exists.
- Not a statement about other hosts: the only transcript shapes read are Claude Code desktop 2.1.330 in permission
  mode auto (two sessions). Codex transcripts were never observed and are unsupported.
- No prompt text, report text, local path, session id, agent id or tool-use id is in these files. Ids are SHA-256
  hashes; skill names are the validated names of the pilot's synthetic catalog; an agent type is written by name
  only when it is a profile id of the session's routes. Task hashes are unkeyed hashes of task text: harmless for
  these synthetic pilot tasks, but files like these should not be shared for a real project, because a guessed task
  text can be confirmed against its hash.
