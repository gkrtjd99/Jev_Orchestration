## 라우팅이 실제로 한 일

- **R**: 12건 모두 route 기록, 재작성, host 거부 1회, 재발행 인식, 라우팅된 프로필로 실행(실행된 agent type = 라우팅된 프로필 12/12, 서브에이전트 행의 effort = route의 effort 12/12). 프로필은 `implement_standard_high` 7건(t01, t02, t04, t05, t09, t11, t12), `implement_standard_xhigh` 5건(t03, t06, t07, t08, t10). 과제 난이도 등급(`tasks.json`의 `difficulty`, 만든 쪽의 의도)과의 대응: hard 4건은 모두 xhigh, routine 4건은 모두 high, moderate는 high 3·xhigh 1(t07).
- **L**: 12건 모두 라우팅되지 않았습니다. 11건은 `no_compatible_profile`로 보류, 1건(t05)은 분류 요청이 1,200 ms timeout(`JEV_TIMEOUT`)이어서 원래 호출이 그대로 통과했습니다. 보류된 호출은 거부도 재발행도 없이 `general-purpose`로 실행됐습니다.
- **L이 보류된 원인(오프라인 재현으로 확인)**: 역할은 11건 모두 implement(확신 1.0)였습니다. 그러나 다섯 답(역할·복잡도·위험·추론·정보) 중 하나라도 확신 0.55 미만이면 "불확실"로 보고 최소 slot을 standard로 올리는 규칙(`optimizer.mjs`의 `eligibleProfiles`)이 있고, 응답한 11건 모두 불확실이었습니다(그중 10건은 "정보" 답이 0.55 미만, 4건은 위험 sensitive). L에는 light만 활성이어서 후보가 0개가 됐습니다. R의 12건도 모두 불확실이었고, 그래서 R에서도 light는 한 번도 고려되지 못했습니다(23/23).
- 즉 **현재 정책과 이 과제 글에서는 이 확장이 구현 작업을 낮은 모델로 내리지 않습니다.** 이것은 측정 결과가 아니라 정책의 동작이고, 내렸을 때 품질이 유지되는지는 이 실험으로 알 수 없습니다.

## 문서와 달랐던 것

1. **Main prompt가 세션에 그대로 전달되지 않았습니다(세 arm 공통).** 세션이 받은 첫 메시지에서 ASCII `@` 4개가 모두 전각 `＠`(U+FF20)로 바뀌어 있었습니다. 또 `main-prompt.txt` 앞에 **세션을 시작한 쪽(실험을 돌린 쪽)이 쓴 배경 문단**이 붙어 있었습니다(세 arm 같은 내용: 폴더가 일회용 합성 프로젝트라는 것, 요청을 적힌 대로 한 번 수행하고 멈출 것, 브랜치를 만들지 말 것, 되묻지 말 것). 이것은 "`main-prompt.txt` 그대로 한 번"이라는 사전 등록에서 벗어난, 실험자 쪽 편차입니다. host는 공유 노트 폴더 안내 한 줄과, R·L에는 연결된 세션 목록을 붙였습니다. `@`가 있는 과제는 12뿐입니다. Main은 받은 글을 그대로 넘겼고, 과제 12의 위임 글이 `tasks.json`과 4글자 달라 분석기가 "위임 안 됨"으로 셌습니다. 서브에이전트는 세 arm 모두 ASCII `@`로 구현했고 채점기는 과제 12를 통과로 봅니다. 치환이 세션을 시작한 쪽(실험자)에서 일어났는지 데스크톱 host에서 일어났는지는 자료로 가릴 수 없습니다. 분석기는 고치지 않았습니다(결과 정의를 건드리지 않기 위해). 그래서 `compare.txt`와 `arm-*.json`의 과제 12 행, 11건 기준 합계, R의 "routed 11", L의 "deferred 10건 목록"은 과제 12가 빠진 숫자입니다.
2. **L의 보류 원인이 예상과 달랐습니다.** 프로토콜 7절은 judge가 review·plan으로 분류할 때만 보류를 예상했습니다. 실제 원인은 "불확실 → 최소 standard" 규칙이었고, 실행 전 설치 점검은 합성 이벤트로만 해서 이것을 잡지 못했습니다. 설계 결함입니다.
3. **L의 과제 5는 judge timeout**이었습니다(보류가 아니라 실패 후 원래 호출 통과).
4. Main이 세 arm 모두 `update_plan` 12회, `wrap_up` 1회를 호출했습니다(데스크톱 앱의 진행 표시 도구). 프로젝트 작업은 하지 않았습니다.

## 독립 검증

세 검증자가 분석기 출력을 믿지 않고 원자료(Main·서브에이전트 기록, hook 상태)에서 직접 계산했습니다.

- 일치: t01~t11의 과제별 토큰·turn·시간, 모델별 11건 합계, Main의 turn·토큰, Agent 호출 12/24/12와 거부 0/12/0, judge 요청·토큰 합계, 수집기의 행 수·context·일치 종류, 고정 파일 해시(`freeze.mjs --check` 통과).
- 불일치: 위 1번에서 나오는 과제 12 관련 숫자 전부. 그 밖에 Main 시간의 정의 차이 약 2.5초.
- 검증에서 드러난 수집기 결함(이 실험 결과에는 영향 없음, 미수정): 검증 항목이 없는 과제를 `withheldTasks`에 세지 않고 조용히 뺌(R 0건·L 11건으로 표시, 실제로는 각각 1건 더). dry run이 관찰 기록 수를 실제 실행과 똑같이 `written`으로 보고함.
- 확인하지 못한 것: 기록된 모델 id·effort가 실제 제공된 것과 같은지(host가 적은 값만 읽음), judge의 usage가 청구와 같은지, 배경 문단과 host가 붙인 글이 Main이나 서브에이전트의 행동에 영향을 줬는지, R·L의 hook 상태에 12건씩 있는 `unverified_prompt` 이벤트의 뜻(분석하지 않음), 과제 5 timeout의 원인.

## 이 실험이 말하지 못하는 것

- 낮은 모델(sonnet)로 내렸을 때의 품질과 비용: 실행 0건.
- 라우팅이 품질을 올리는지: 세 arm 모두 만점(사전 등록 집계로는 11/12)이라 차이가 날 자리가 없었습니다. 과제 12개가 fable medium에게 너무 쉬웠습니다.
- 다른 Main 모델, 다른 권한 모드, 실제 저장소, Codex.
