# Skill 주입 paired pilot 보고서 (2026-11-25)

질문은 하나입니다. subagent에게 가는 위임 prompt에 `<jev-skills>` 블록을 붙이면 결과가 달라지는가. 사전 등록 프로토콜은
[PROTOCOL.md](PROTOCOL.md), 결과 파일은 [`../results/pilot-20261125/`](../results/pilot-20261125/)에 있습니다. arm당 1회 실행, 짝 6개라서
아래 숫자는 모두 기술 값이고 유의성 주장은 없습니다. 측정하지 못한 값은 "미측정"이라고 적었고 0이나 실패로 세지 않았습니다.

## 1. 먼저: 두 arm이 skill 블록 말고 달랐던 것

프로토콜 규칙 7에 따라 결과보다 먼저 적습니다.

- **t04는 같은 조건의 짝이 아닙니다.** arm A에서는 라우터가 판단을 보류해(`selector_abstained`) subagent가 `general-purpose`,
  `claude-fable-5-2`, effort `medium`으로 routing packet 없이 실행됐습니다. arm B에서는 `jev4_implement_standard_xhigh`,
  `claude-opus-5-5`, effort `xhigh`로 실행됐습니다. t04의 2차 측정(도구 호출, 토큰, 시간)은 블록의 효과로 읽을 수 없습니다.
- 나머지 7개 짝은 두 arm에서 profile, 모델, effort가 같았습니다.
- **사전 등록한 위임 형태는 16건 중 1건(arm A t04)에서만 지켜졌습니다.** 나머지 15건은 hook이 Agent 호출을 고쳤고, 권한 모드
  `auto`의 harness가 그 호출을 실행 전에 거부했고, Main이 hook이 만든 입력으로 다시 호출했습니다. 그래서 subagent는
  `general-purpose`가 아니라 `jev4_*` profile로, 과제 문장 뒤에 routing packet이 붙은 prompt로 시작했습니다. 블록이 간 짝이 실제로
  비교하는 것은 "routing packet" 대 "routing packet + 블록"입니다.
- Main prompt는 `main-prompt.txt`를 글자 그대로 포함하지만 앞뒤에 실행기 문구가 붙었습니다(A +689자, B +963자). B에만 상대 세션을
  가리키는 알림이 있었습니다.
- arm A는 앞선 실제 세션 확인(3회)에 쓰던 폴더 경로에서 실행됐습니다. 폴더 내용은 `template/`의 새 사본이었지만 경로는 새것이
  아니었고, 경로에 묶인 harness 상태가 남아 있었는지는 미측정입니다. arm B는 새 폴더였습니다.

## 2. 결론

두 arm 모두 skill 과제 6개 중 6개가 규칙 검사를 통과했고, 주입이 없는 arm A에서도 skill 과제의 subagent 6개 전부가 harness가 보여
준 skill 목록에서 target skill을 골라 `Skill` 도구로 직접 load했습니다(5건은 첫 도구 호출, 1건은 두 번째). 그래서 이 설정에서
주입 블록은 subagent가 이미 스스로 한 일과 겹쳤고, 이 pilot은 주입의 이득을 재지도 못했고 이득이 없다고 보여 주지도 못했습니다.
baseline이 이미 만점이라 차이가 날 자리가 없었기 때문입니다. target이 목록에 보이지 않거나 subagent가 스스로 load하지 않는 상황에
대해서는 아무 정보도 주지 않습니다. 관찰된 비용은 arm B에서 skill judge 요청 32건(Agent 호출당 2건, 지연 합 12,008 ms, 토큰은
미측정)이고, 관찰된 절감은 없습니다. subagent 비용 차이는 블록이 없던 짝들 사이의 실행 간 편차와 같은 크기였습니다.

## 3. 무엇을 돌렸나

- 실제 Claude Code 데스크톱 세션 두 개. arm A(baseline)는 `delegation.skills` 지점 off, arm B(assisted)는 active. 설치된 설정 파일은
  경로 말고 같았고, 다른 것은 env 한 줄(`JEV_SKILLS_MODE`)이었습니다. 전역 모드는 둘 다 `active`, judge는 실제 Jev입니다.
- 합성 프로젝트 `parceldesk`와 skill 60개(target 6, distractor 54). 과제, skill, 채점기는 모두 모델이 만든 합성 자료입니다.
- 세션마다 위임 8건을 정해진 순서로: skill 과제 6개와 control 2개.
- `jev4_*` agent profile 27개를 실행하는 동안만 사용자 수준 `~/.claude/agents`에 설치했고 끝난 뒤 제거했습니다(이 보고서를 쓸 때
  그 폴더가 없음을 확인).
- 두 arm은 동시에 시작했습니다(첫 hook 이벤트 간격 2.5초). 소요 시간은 서로 영향을 받았을 수 있습니다.
- Main은 `claude-fable-5-2`, effort `medium`, 권한 모드 `auto`. hooks는 버전 3.2.0(`orchestration/` 트리 `382fa56`).
- 소유자 환경의 사용자 수준 skill, plugin, MCP는 끄지 않았습니다(skill 검색용 MCP와 그것을 쓰라는 skill 포함). 읽기 조언은 두 arm
  모두 꺼져 있었습니다.
- 세션은 arm당 한 번만 실행했고 다시 돌리지 않았습니다. 이 보고서를 쓰는 단계에서는 세션도 실제 API 호출도 없었습니다.

## 6. 2차 측정

**모든 2차 측정은 세션 뒤에 정한 연결 규칙으로 읽은 값입니다.** 프로토콜은 "과제 문장이 든 첫 Agent 호출"을 그 과제의 호출로
정했는데, 실제로는 첫 호출이 실행 전에 거부됐습니다. 글자 그대로 적용하면 subagent 측정이 16건 중 15건에서 미측정이 됩니다.
분석기는 "실행 전에 거부되지 않은 첫 호출"을 씁니다. 1차 결과는 프로젝트 폴더에서 읽으므로 이 규칙과 무관합니다.

## 7. arm A는 주입 없이 어떻게 규칙을 지켰나

harness가 hook과 무관하게 모든 subagent에게 skill 목록을 줬습니다. 16개 subagent 전부가 이름 101개가 든 목록을 받았고, 프로젝트
skill 60개는 전부 설명과 함께 들어 있었습니다(나머지 41개는 소유자 환경의 사용자 수준·plugin skill). arm A의 skill 과제 subagent는
그 목록에서 target을 골라 `Skill` 도구로 load했습니다. 5건은 첫 도구 호출, t01은 `Bash`로 한 번 둘러본 뒤 두 번째 호출이었고, 6건
모두 첫 파일 쓰기보다 앞섰습니다. 다른 프로젝트 skill은 load하지 않았습니다.

routing packet이 없던 arm A t04(`general-purpose`)도 첫 호출로 target을 load했습니다. 한 건의 관찰이지만, 스스로 load하는 데
routing packet의 "먼저 지침을 읽으라"는 문장이 꼭 필요하지는 않았다는 뜻입니다.

프로토콜이 "확인 대상"으로 둔 가정(harness가 skill 목록을 보여 주므로 어느 arm에서든 스스로 load할 수 있다)은 이 실행에서
성립했습니다. 60개는 목록이 잘리는 크기가 아니었습니다.

## 8. 주입이 더한 비용과 관찰된 절감

더한 비용 (arm B, hook 결정 기록 기준):

- skill judge 요청 32건 = Agent 호출 16건 × 2건. 절반(16건)은 거부된 시도에서 나갔고 그 판단만 subagent에 전달됐습니다. 나머지
  16건은 다시 호출될 때 블록이 이미 든 prompt에 대해 한 번 더 판정한 것이고 적용되지 않았습니다.
- 지연 합 12,008 ms(요청당 평균 375 ms, 최대 1,133 ms). 실제로 시작된 호출 8건 몫은 5,120 ms입니다.
- Agent 호출 한 건의 hook 시간: A 평균 598 ms(14건 합 8,365 ms), B 평균 686 ms(16건 합 10,968 ms). skill 요청 두 건의 지연 합이 hook
  시간보다 커서 라우팅과 함께 병렬로 나간 것으로 보입니다.
- judge 토큰은 미측정입니다.

관찰된 절감: **없습니다.**

- load 위치가 두 arm에서 같았으므로 "더 빨리 load"는 일어나지 않았습니다.
- 조건이 같고 블록이 간 4개 짝(t02, t05, t06, t08)의 B − A 합: 도구 호출 −6, 턴 +2, 토큰 +79,280, 출력 토큰 −455, 시간 −2.3초.
  방향이 섞여 있습니다.
- 블록이 어느 arm에도 없고 조건이 같은 3개 짝(t01, t03, t07)의 토큰 차이는 −60,496(−7.7%), +70,707(+23.7%), +5,053(+1.7%)입니다. 같은
  prompt로 달라진 것은 실행뿐인데 이만큼 다릅니다. 위 4개 짝의 차이는 이 범위 안에 있어 블록 때문이라고 할 수 없습니다.
- 토큰 합의 87.6%(A), 91.2%(B)가 cache 읽기입니다. 이 합은 턴 수를 따라가는 값이지 청구 비용이 아닙니다. 예: t02는 도구 호출이
  11건으로 같지만 B가 10턴, A가 7턴이어서 +186,343입니다.
- 8개 합의 차이 +872,132 중 +777,588이 조건이 다른 t04입니다.
- Main 세션: A 2,477,558 토큰 / 508.6초, B 2,631,871 토큰 / 616.2초. B에는 t04의 긴 subagent가 들어 있습니다.

## 9. 프로토콜에서 벗어난 것

1절의 항목에 더해:

- Agent 호출 수: A 15건(거부 7 + 시작 8), B 16건(거부 8 + 시작 8). 과제당 시작된 호출은 1건이었습니다. 프로토콜은 과제당 1건을
  요구했습니다. 거부는 모두 자동이었고 Main의 선택이 아니었습니다. 다시 호출한 입력은 15건 모두 hook이 만든 입력과 글자까지
  같았으므로 Main이 덧붙인 것은 없습니다.
- t01은 두 arm 모두 hook의 두 번째 route(standard / opus / high)와 다르게 첫 시도의 route(light / `claude-sonnet-5-5` / xhigh)로
  실행됐습니다. 두 arm에서 같습니다.
- Main이 쓴 다른 도구는 계획 표시용 `update_plan` 8회와 `wrap_up` 1회뿐이고 직접 작업은 없었습니다. 사용자 prompt는 arm당 1개,
  순서는 지켜졌습니다.
- 소유자가 개입한 확인 창은 보이지 않습니다. arm B t04 subagent의 `update_plan` 호출 1건이 hook에 의해 거부됐습니다.
- hook 상태 폴더마다 준비 단계의 세션 하나(`session_started` 이벤트 1개)가 더 있습니다. 과제 이벤트는 없습니다.
- 분석기를 세션 뒤에 두 번 고쳤습니다(읽기 방식과 연결 규칙, 그다음 독립 검증 뒤의 표시 방식). 과제, skill, 채점기,
  `main-prompt.txt`, 결과 정의는 바꾸지 않았습니다. 내용은 PROTOCOL.md 끝과 `../results/pilot-20261125/notes.txt`에 있습니다.

## 10. 이 pilot이 보여 주는 것과 보여 주지 못하는 것

보여 주는 것:

- 실제 세션의 `active` 모드에서 hook의 재작성이 subagent에게 전달됩니다. 다만 권한 모드 `auto`에서는 "거부 후 재호출"을 거치고,
  그 때문에 hook과 judge가 위임마다 두 번 실행됩니다.
- 이 설정(skill 60개, harness 목록에 전부 노출, 추측할 수 없는 규칙)에서는 subagent가 주입 없이도 맞는 skill을 찾아 load했고
  규칙을 지켰습니다.
- skill judge는 skill 과제 6개 중 5개에서 target을 골랐고 control 2개에는 주입하지 않았습니다. 놓친 1건(t01)은 need 점수가 임계값
  아래였습니다.

보여 주지 못하는 것:

- **주입이 도움이 되는지.** 두 arm이 모두 6/6이라 천장 효과입니다. "효과 없음"의 증거도 아닙니다.
- 주입이 비용이나 시간을 줄이는지. 차이가 실행 간 편차 안에 있고 arm당 1회입니다.
- 짝 6개(블록이 실제로 갈린 것은 5개, 그중 조건이 같은 것은 4개), 1회 실행이라 어떤 비율도 일반화할 수 없습니다.
- 과제와 skill이 합성 자료입니다. 실제 프로젝트의 과제나 skill에 대해서는 말할 수 없습니다.
- 사용자 수준 skill 검색 도구를 켜 둔 채였습니다. 이번에는 아무 subagent도 쓰지 않았지만, 꺼 둔 환경과 같다고 할 수는 없습니다.
- harness 목록이 잘리는 크기의 카탈로그, 목록에 없는 skill, subagent가 스스로 load하지 않는 과제에서 무슨 일이 생기는지.

## 11. 효과를 볼 수 있으려면 다음 실험이 바꿔야 할 것

1. **baseline에 틀릴 자리가 있어야 합니다.** 본 실험 전에 baseline만 돌려 convention 통과가 만점이 아닌 과제 세트를 확인합니다.
   후보: harness 목록이 잘릴 만큼 큰 카탈로그, 목록에 실리지 않는 위치의 skill(`JEV_SKILL_DIRS`), 설명이 과제 문장과 겉으로 닮지
   않은 skill.
2. **arm당 여러 번 실행합니다.** control 짝 하나가 토큰 +23.7%를 보였으므로 1회로는 비용 차이를 읽을 수 없습니다.
3. **두 arm의 라우팅을 고정합니다.** t04처럼 한쪽만 보류되면 짝이 깨집니다. profile, 모델, effort를 arm 사이에 같게 강제합니다.
4. **"거부 후 재호출"을 없애거나 계산에 넣습니다.** 지금은 위임 한 번에 hook이 두 번 돌고, 적용되지 않는 두 번째 판단이 기록에
   남습니다. 사전 등록 규칙도 이 흐름을 전제로 다시 써야 합니다.
5. **judge 토큰을 결정 기록에 남깁니다.** 지금은 주입의 비용을 요청 수와 지연으로만 말할 수 있습니다.
6. **사용자 수준 skill 검색 도구를 끄고**, arm마다 새 경로를 씁니다.
7. 합성 과제 말고 실제 프로젝트의 과제를 포함하고, 통과/실패보다 촘촘한 결과(규칙 위반 수, 재작업 횟수)를 함께 봅니다.

## 12. 독립 검증과 그 뒤의 정정

독립 검증이 분석기를 쓰지 않고 원자료에서 숫자를 다시 계산했고, 커밋된 값(채점, 과제와 subagent의 연결, 과제별 도구 호출·토큰·시간,
load 경로와 위치, 주입 내용)이 재현됐습니다. 보고된 문제 10건은 모두 원자료로 다시 확인했습니다.

| # | 지적 | 처리 |
|---|---|---|
| 1 | "주입이 결과를 바꾸지 않았다"는 효과 없음으로 읽힘 | 사실. 결론을 "이 설정에서는 겹쳤고, 이득을 잴 수도 배제할 수도 없다"로 씀 |
| 2 | t04의 차이가 결과 뒤에 적혀 있고 effort 차이는 빠짐 | 사실(effort `medium` 대 `xhigh` 확인). 표와 문서 맨 앞으로 옮기고 effort를 분석기에 추가 |
| 3 | 비용 차이는 1회 실행의 편차 안 | 사실(t03 +23.7%, t02 턴 7 대 10 확인). 비용을 방향 없는 기술 값으로만 적고 턴 수와 출력 토큰을 함께 표시 |
| 4 | 연결 규칙이 사후에 정해짐 | 사실. 2차 측정 전체에 표시 |
| 5 | 과제별 `hook`이 적용되지 않은 두 번째 hook 실행의 것 | 사실. `hookApplied`를 더하고 표의 주입 열을 그것으로 바꿈. 개수(5/6, 0/2)는 그대로 |
| 6 | arm A가 재사용된 경로에서 실행됨 | 사실. 여기와 `notes.txt`에 밝힘. 경로에 남은 상태는 미측정 |
| 7 | 사전 등록한 위임 형태가 실현되지 않음 | 사실. 1절에 적음 |
| 8 | Main 소요 시간이 3.5초, 2.6초 김 | 사실. 기준 행을 맞춰 508.6초, 616.2초로 정정(이전 512.1, 618.8) |
| 9 | 정리본에 소유자 skill 이름 41개가 16번 실림, README에 로컬 경로 | 사실. 이름 목록을 개수와 검색용 skill 이름 2개로 줄이고 경로를 자리표시자로 바꿈 |
| 10 | 설치된 설정의 `read.advice` 지점이 `active` | 문제 아님. 최상위 `readAdvice`가 `false`면 그 지점에 도달하지 않고, 설치된 matcher에 `Read`가 없고, 읽기 조언 이벤트가 0건. 읽기 조언은 꺼져 있었음 |

이 정정으로 바뀐 숫자는 Main 소요 시간뿐입니다.
